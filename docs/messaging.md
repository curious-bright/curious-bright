# Private one-to-one messaging

Private messaging is intentionally separate from study-room chat. A
conversation has exactly two participants; there are no group DMs, organization
inboxes or staff backdoors. Platform staff may see reports through the admin
moderation tools, but organization admins/owners cannot read member
conversations.

## 1. Data model

| Model | Purpose |
|---|---|
| `Conversation` | Unique canonical pair of users (`user_a_id < user_b_id`) |
| `ConversationParticipant` | Participant row with `last_read_at` |
| `Message` | Text body (≤ 4,000 chars), optional `client_id` for idempotency, timestamps and tombstone fields |
| `UserBlock` | Directional block; either direction blocks new messages |
| `MessageReport` | Report reason/status for moderation |

`Profile.message_privacy` controls new conversations:

- `anyone` — default; any active account can start a conversation.
- `follows` — only people the target follows can start a conversation.
- `nobody` — no new conversations can be started.

The privacy setting only applies when **starting** a conversation. Existing
conversations remain available unless either participant blocks the other. A
block blocks new messages in both directions but preserves history.

Deleting your own message is a delete-for-everyone tombstone: `body` is
cleared, `deleted_at`/`deleted_by` are recorded, and the websocket/API returns
an empty `deleted` message so the other side can render a tombstone. You cannot
delete the other participant's messages. There is no “delete for me only” mode
yet.

## 2. API

All endpoints require authentication and are prefixed with `/api/`.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `messages/conversations/` | List up to 100 conversations, newest activity first |
| `POST` | `messages/conversations/` | Start/find a conversation: `{username, message?}` |
| `GET` | `messages/conversations/<id>/` | Conversation summary; participant only |
| `GET` | `messages/conversations/<id>/messages/?before=&limit=` | Paginated history, limit ≤ 100 |
| `POST` | `messages/conversations/<id>/messages/` | Send `{body, client_id?}` |
| `POST` | `messages/conversations/<id>/read/` | Mark incoming messages read |
| `DELETE` | `messages/<message_id>/` | Tombstone your own message |
| `POST` | `messages/<message_id>/report/` | Report a message `{reason}` |
| `GET` | `messages/unread/` | Total and per-conversation unread counts |
| `GET` | `messages/blocks/` | Accounts you blocked |
| `POST/DELETE` | `messages/blocks/<username>/` | Block/unblock an account |

Every read path uses a participant filter. A non-participant gets `404`, not a
403, to avoid leaking conversation existence. Only the owner of a message can
delete it.

`client_id` is a UUID generated by the client. Retrying the same
`client_id` returns the existing message rather than creating a duplicate, which
makes flaky mobile sends safe.

## 3. Realtime

WebSocket prefix: `/ws/`, authenticated with `?token=<access>`.

| Socket | Events |
|---|---|
| `/ws/messages/` | `messages.connected` with unread total, `conversation.unread`, `message.created`, `message.read`, `message.deleted` |
| `/ws/conversations/<id>/` | `conversation.connected`, `conversation.typing`, `message.read` |

The conversation socket checks participant membership during connection and
closes with 4403 for outsiders. The message list itself is still fetched over
REST; the socket is for live updates and typing. Clients should also refresh
history when reconnecting because messages sent while offline are not replayed
by the socket.

`message.created` is published to the participant groups and to each user's
`messages.user.<id>` group so the conversation list/unread badge updates even
when the other conversation pane is not open. Redis is required for this to
work across multiple ASGI workers.

## 4. Member UI

The Messages page (`apps/web/src/pages/Messages.tsx`) supports:

- conversation list with last message, timestamp and unread badge;
- a thread view with sent/read indicators and tombstones;
- typing indicator and live send/receive;
- starting a conversation from a profile or a study-room member list;
- delete own message, block/unblock and report;
- an empty state explaining the privacy setting;
- mobile bottom-tab entry with unread badge and desktop navigation entry.

Settings → Privacy includes “Who can message me” with **Anyone**, **People I
follow**, and **Nobody**. The default is **Anyone** so direct messages work for
new accounts. Existing conversations remain open after changing the setting.

## 5. Moderation and privacy boundaries

- Organization admins, teachers, moderators and owners are not participants and
  cannot query conversations through the API.
- Platform staff can inspect message reports in Django admin. Message bodies are
  readonly in that admin view. A report notification is generated for
  moderators; resolution is audited.
- Do not log message bodies, participants, message IDs with user identifiers, or
  report reasons in application logs/analytics.
- Backups containing the messaging tables are private. Apply the same retention
  and access controls as other private user data.
- The service worker must never cache `/api/messages/*` responses. The current
  service worker skips every `/api/` path and cross-origin API requests.

## 6. Deployment checklist

- [ ] `REDIS_URL` is set on every ASGI worker; otherwise unread updates can be
      lost between workers.
- [ ] `WS_ALLOWED_ORIGINS` includes the member app, portal and any preview
      origin. The Django ASGI server must be the WebSocket endpoint.
- [ ] The reverse proxy forwards `/ws/` with upgrade headers and a timeout
      longer than the websocket heartbeat.
- [ ] `CORS_ALLOWED_ORIGINS`/`CSRF_TRUSTED_ORIGINS` include the deployed origins.
- [ ] The load balancer does not buffer or strip `Upgrade`/`Connection` headers.
- [ ] Run at least one smoke test with two browser sessions: send, receive,
      typing, read receipt, unread badge, block, report and tombstone.
- [ ] Verify a non-participant gets 404 on conversation reads and a 4403 socket
      close.
- [ ] Verify organization admins cannot read member conversations.
- [ ] Check that analytics never receives message content or participant data.
